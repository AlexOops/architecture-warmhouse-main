# Архитектура приложения

Документ описывает текущее состояние системы компании «Тёплый дом», анализ существующего монолитного решения и шаги по
проектированию целевой архитектуры экосистемы умных домов.
В документе последовательно рассматриваются функциональность текущего приложения, выявленные ограничения и архитектурные
проблемы, а также предлагается разделение системы на домены и контексты и формируется базовая модель архитектуры
будущего решения.

## Анализ и планирование

В данном разделе проводится анализ текущей функциональности и архитектуры монолита, определяется предметная область,
выделяются границы контекстов и фиксируются ключевые проблемы, препятствующие масштабированию и развитию системы.

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

* Пользователи могут: включать/выключать отопление в доме через веб-интерфейс.
* Система поддерживает: передачу команд на модуль управления отоплением в конкретном доме

**Мониторинг температуры:**

* Пользователи могут: смотреть текущую температуру в доме.
* Система поддерживает: получение данных с датчиков, сохранение в БД, выдачу по запросу.

### 2. Анализ архитектуры монолитного приложения

* Язык: Go
* БД: PostgreSQL
* Архитектура: монолит, все модули внутри одного приложения.
* Взаимодействие: синхронные запросы, без очередей и событий.
* Масштабирование и развёртывание: масштабируется целиком, обновление требует остановки всего сервиса и т.д.

### 3. Определение доменов и границы контекстов

1. Domain: Управление устройствами (Device Management)
   `Контекст: регистрация устройств, управление состоянием, телеметрия, взаимодействие с датчиками.`
2. Domain: Управление отоплением (Heating Control)
   `Контекст: логика управления отоплением, сценарии, поддержка целевых устройств.`
3. Domain: Управление освещением (Lighting Control)
   `Контекст: управление световыми устройствами, режимы, сценарии.`
4. Domain: Управление воротами и доступом (Gate Control)
   `Контекст: управление воротами, механизмы доступа.`
5. Domain: Видеонаблюдение (Surveillance)
   `Контекст: работа с видеопотоками и событиями камер.`
6. Domain: Пользователи и доступ (Identity & Access)
   `Контекст: аутентификация, авторизация, пользовательские роли, привязка домов и устройств.`
7. Domain: Биллинг и SaaS-модули (Billing)
   `Контекст: подписки, тарифы, управление доступными модулями экосистемы.`

### **4. Проблемы монолитного решения**

* Ограниченная масштабируемость.
* Сложность добавления новых типов устройств и модулей.
* Отсутствие асинхронности (неудобно для IoT).
* Обновление --> остановка всего приложения.
* Зависимость команд по установке, нет self-service для пользователей и т.д.

# Задание 4. Создание и документирование API

### 1. Тип API

В экосистеме «Тёплый дом» используется гибридный подход к интеграции микросервисов:

- **REST API (OpenAPI)** — для синхронных запросов/ответов.
  Он применяется для:
    - взаимодействия клиентского приложения (Web/PWA) с API Gateway,
    - выполнения CRUD-операций над сущностями (пользователи, дома, устройства, настройки),
    - получения агрегированных данных для интерфейса.

- **Событийное взаимодействие (AsyncAPI)** — для асинхронной обработки доменных событий.
  Оно используется для:
    - приёма телеметрии от устройств,
    - публикации доменных событий (например, `DeviceRegistered`, `DeviceStateChanged`, `TelemetryReceived`),
    - реакций профильных сервисов (отопление, освещение, уведомления) на события без жёстких синхронных связей.

Такой подход позволяет сочетать простоту и предсказуемость REST для запросов/ответов с масштабируемостью и слабой
`связанностью` событийной архитектуры для обработки телеметрии и внутренних доменных событий.

### 2. Документация API

Документация подготовлена с использованием **Swagger/OpenAPI** для REST API и **AsyncAPI** для событийных каналов.

#### 2.1. Device Management Service (REST, OpenAPI)

Микросервис отвечает за регистрацию устройств, управление их состоянием и привязку к домам.

Файл спецификации: [openapi.yaml](/apps/device-management/api/openapi.yaml)

Примеры операций:

- `GET /devices/{id}` — получить информацию об устройстве.
- `GET /houses/{houseId}/devices` — получить список устройств в доме.
- `POST /devices` — зарегистрировать новое устройство.
- `PATCH /devices/{id}/state` — обновить состояние/статус устройства.
- `GET /device-types` — получить список поддерживаемых типов устройств.

#### 2.2. Heating Service (REST, OpenAPI)

Микросервис управляет отоплением в доме: режимами работы и целевой температурой.

Файл спецификации: [openapi.yaml](/apps/heating-service/api/openapi.yaml)

Примеры операций:

- `GET /houses/{houseId}/heating` — получить текущее состояние системы отопления дома.
- `POST /houses/{houseId}/heating/commands/setpoint` — изменить целевую температуру.
- `POST /houses/{houseId}/heating/commands/mode` — изменить режим работы (auto/manual/off).

#### 2.3. Telemetry / Events (AsyncAPI)

Микросервис телеметрии и событийная шина обеспечивают приём показаний с устройств и публикацию доменных событий, на
которые подписываются другие сервисы (отопление, уведомления и т.д.).

Файл спецификации: [asyncapi.yaml](/apps/telemetry-service/api/asyncapi.yaml)

Примеры каналов:

- `telemetry.device.{deviceId}.temperature`  
  — канал публикации показаний температуры от устройств.

- `device.events`  
  — канал доменных событий устройств (например, `DeviceRegistered`, `DeviceStateChanged`).

Каждый канал описан в AsyncAPI-спецификации с указанием форматов сообщений (JSON-payload), схем данных и ролей
издателей/подписчиков.

# Задание 5. Работа с docker и docker-compose

Был реализован сервис `temperature-api`, который по запросу `GET /temperature?location=&sensorId=` возвращает случайное
значение температуры. Логика сопоставления `location` и `sensorId` реализована в соответствии с условиями задания: при
отсутствии `location` оно подбирается по `sensorId` (1 — Living Room, 2 — Bedroom, 3 — Kitchen), при отсутствии
`sensorId` — наоборот.

Сервис упакован в отдельный Docker-образ (`apps/temperature-api/Dockerfile`) и добавлен в `docker-compose.yml` с портом
`8081`. Для приложения `smart_home` в `docker-compose.yml` также добавлен сервис `postgres` (образ `postgres:16-alpine`)
с инициализацией схемы из `./apps/smart_home/init.sql`. Приложение `smart_home` получает строку подключения к базе через
переменную окружения `DATABASE_URL`, а адрес сервиса температуры — через
`TEMPERATURE_API_URL=http://temperature-api:8081`.

Проверка выполнялась через коллекцию `smarthome-api.postman_collection.json` с вызовами `Create Sensor` и
`Get All Sensors`. При каждом вызове `Get All Sensors` температура меняется, так как `smart_home` обращается к
`temperature-api`, который каждый раз генерирует новое случайное значение.
